# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```
pip install -e ".[dev]"          # install app + dev deps (pytest, httpx) from pyproject.toml
pytest                           # run the full test suite
pytest tests/test_prompts.py     # run a single test file
pytest tests/test_prompts.py::test_parse_response_splits_positive_and_negative  # run a single test
uvicorn app.main:app --reload    # run the dev server at http://localhost:8000
docker compose up --build        # build and run the containerized app (reads .env, mounts ./data)
Start.bat / Stop.bat             # Windows: the way the app actually runs (see below)
```

**Where it runs.** On the owner's Windows PC (LENOVO LEGION), next to ComfyUI and comfy-gateway, straight from this checkout: `Start.bat` keeps a `.venv` here (reinstalled from `requirements.txt` whenever it differs from the copy saved as `.venv\requirements.installed`), runs `uvicorn` on port 8090 of every interface (`0.0.0.0`, so the owner's phone reaches it over the home network; plain HTTP behind the Basic Auth, and Windows' firewall lets it in through the allow rule for the Store Python's exact version, which asks again on the PC when that Python updates) in a minimized window titled "prompt-enhancer (servidor)", and opens the browser on `127.0.0.1:8090` once it answers; both scripts find the server by what listens on `:8090`, and `Stop.bat` kills it and leaves a mark in `%TEMP%` so that window closes itself (an unexpected stop leaves it open, paused, to read why). The running instance's `data/` and `.env` are this checkout's (both gitignored), so restarting picks up whatever code is checked out here, and `tests/conftest.py` overrides the real `OPENROUTER_API_KEY`/`ADMIN_PASSWORD` for every test. Until 2026-11-03 it ran in Docker on the home server cubi-n (the stopped container and a copy of its data remain there).

Copy `.env.example` to `.env` before running anything — `OPENROUTER_API_KEY`, `ADMIN_USERNAME`, `ADMIN_PASSWORD` (plus optional `DEFAULT_LLM_MODEL`/`DEFAULT_VISION_MODEL`, the models prefilled in the UI, and `COMFY_GATEWAY_URL`/`COMFY_DIRECT_URL`, which let Conversar's bot run ComfyUI workflows; unset, that whole part is off -- with `COMFY_JOB_TIMEOUT_MINUTES`, how long a job may run without a result, 45 by default; and `CLAUDE_CODE_CONFIG_DIR`/`CLAUDE_CODE_MODEL`/`CLAUDE_CODE_COMMAND`/`SELF_URL` for Claude Code as the bot, below). `tests/conftest.py` unsets the ComfyUI variables for every test; tests that need ComfyUI use the `fake_comfy` fixture (a `FakeComfy` standing in for `comfy.Comfy`), and `png_bytes(**texts)` makes real PNGs with text chunks. The app refuses to start (raises in `lifespan`) if `ADMIN_PASSWORD` is unset, so tests set all three via `monkeypatch.setenv` in `tests/conftest.py`'s `api_client` fixture rather than relying on a `.env` file.

## Architecture

FastAPI + Jinja2 + vanilla JS. No build step (no bundler, no npm), no database — every persistent thing is a flat JSON or JSONL file under `data/` (gitignored, Docker-volume-mounted). `app/storage.py` is the only place that touches the filesystem for JSON: `read_json`/`write_json` (atomic via tempfile + `os.replace`) for families, notes and the bot's personality, `append_jsonl`/`read_jsonl`/`write_jsonl` (atomic rewrite) for history, plus `write_bytes`/`remove` for the images shared in Conversar. Every domain module (`families.py`, `history.py`, `system_prompt.py`, `memory.py`) follows the same shape: a `_default_path()` derived from `get_settings().data_dir`, plain functions that accept an optional `path` override (this is how tests get isolation — `tests/conftest.py` sets `DATA_DIR` to `tmp_path` per test rather than every module needing a path argument at the call site), and no classes/ORM — just lists/dicts of plain data read-modify-written wholesale on every mutation. `workflows.py` (`data/workflows.json`, the ComfyUI workflow library, seeded once from `app/seed_workflows/` -- the owner's workflows, taken from the sibling image-generation project -- when the file doesn't exist) and `catalog.py` (`data/catalog.json`) follow it too. The exception is `conversations.py`: a conversation grows with every message, so each one is its own `data/conversations/<id>.json` (images in `data/conversations/<id>/`, each with a `-small.jpg` copy when large and a `.workflow.json` when it embeds a ComfyUI workflow, plus `run-<n>.json`, the workflows sent for run n), read-modify-written under a lock; ids are validated as UUIDs before they touch a path, and functions take an optional `root` folder override instead of `path`. `request_log.py` (below) is the other one: a JSONL file per day plus an image folder. Because every OpenRouter call now writes to disk, `tests/conftest.py` points `DATA_DIR` at `tmp_path` for every test (autouse), not only for `api_client`.

**Request flow.** `app/main.py` wires a single FastAPI app with a global `Depends(require_auth)` dependency, so *every* route (including static files and page routes) is behind HTTP Basic Auth — there's no per-route auth annotation to forget. `app/auth.py` compares credentials with `secrets.compare_digest` against `Settings.admin_username/admin_password`. A middleware in `main.py` logs method/path/status/duration for every request and sets `Cache-Control: no-cache` on `/static/*` (no hashed filenames, so browsers must revalidate after a deploy); `main.py` also pins `.js` to `text/javascript`, since the frontend is ES modules and Windows can map `.js` to `text/plain`. On startup, `lifespan()` calls `seed.ensure_seed_data(data_dir)`, which creates `families.json` (seeded with SDXL and Z-Image-Turbo, each with hardcoded `*_INSTRUCTIONS` text) only if it doesn't exist, and fills `system_prompts.json` **per mode** from `seed.DEFAULT_SYSTEM_PROMPTS` -- only `conversation`, the bot's personality, is left: modes missing from the file are added, modes already present (edited or not) are never touched, so changing a default doesn't reach deployments seeded earlier (they keep their text until someone loads the original in Ajustes). The one-shot modes of the retired Crear page (`generate`, `image`, `story`, `variations`, `extract_character`, and the older `iterate`) left their keys in older deployments' files; nothing reads them, as nothing reads `data/characters.json` since characters went (2026-11-04: the bot keeps what it needs about a character in the conversation and its notes).

**What went** (2026-11-04). The app began as a one-shot prompt generator: a "Crear" page with four modes (Generar, Imagen, Historia, Variaciones; an earlier "iterate" refine moved to Conversar), each a single OpenRouter call (`call_openrouter`) through `routes/api.py`, plus reusable "Personajes" inlined into prompts. Conversar does all of it with iteration, images and runs, and the history showed the one-shot modes barely used, so both went: endpoints, pages, their system prompts, the MCP tools for them, and `call_openrouter`. Their history entries remain (modes `generate`, `image`, `story`, `variations`, `iterate`), shown by Historial as before; Peticiones keeps the labels of their old log entries.

**`routes/api.py`** is what the pages share: `_require_family` (404 if unknown) and `read_image` (type and size checks) for the other routers, `GET /api/openrouter-models` (`openrouter_client.list_models()`, cached in-process for `MODELS_CACHE_TTL_SECONDS`, annotating each model with `supports_images` and `supports_tools`), and the history: `GET /api/history` returns entries newest-first; `PATCH /api/history/{id}` (`{favorite}`) and `DELETE /api/history/{id}` rewrite the JSONL under a lock in `history.py`. Entries written before the `prompts` list existed (a top-level `positive_prompt`/`negative_prompt`, or a story's `episodes`) are normalized on read by `history._normalize`, and migrated on disk the first time any entry is favorited or deleted. Conversar writes one entry per reply that proposes prompts (`mode: "conversation"`, with the conversation's id and title in `params`).

`has_negative_prompt` (set per-family in `families.json`/Ajustes) is the single flag that drives negative-prompt suppression: `prompts.parse_response` (the text of a `<prompt>` block, read by `chat.parse_reply`) always parses out whatever the LLM put after `NEGATIVE:`, but forces it to `""` when the family says it doesn't use one (e.g. Z-Image-Turbo, whose instructions also tell the LLM not to bother generating one — the code-level suppression is the actual guarantee, not the prompt wording). The frontend hides the negative block when it's empty.

`openrouter_client.stream_chat(api_key, model, messages, temperature, context, tools, tool_choice)` is how Conversar calls OpenRouter: it takes a full chat `messages` list (`max_tokens` 8192, 180 s timeout), reads OpenRouter's server-sent events and yields each text delta, then one `StreamEnd(cost, truncated, request_id, tool_calls)` -- `usage.cost` threaded back as `cost`, `truncated` mirroring `finish_reason == "length"`; with `tools` (OpenAI-style function definitions) the model may call them, and the calls, which arrive in pieces, come back assembled as `[{id, name, arguments}]`. HTTP errors raise at once as `RuntimeError` with a user-facing message (`_raise_for_status`); it never retries (part of the reply may already be on screen), and raises for an error reported mid-stream or a dropped connection. Every request sends `provider: PROVIDER_PREFERENCES` (`{"data_collection": "deny"}`): OpenRouter only routes to providers that neither store nor train on the data, since prompts and images are personal; a model with no such provider fails with an explained 404.

**Request log** (`request_log.py`, `routes/requests.py`, the Peticiones page). Every HTTP request to OpenRouter is recorded *as sent*, not reconstructed: `stream_chat` opens a `RequestRecord(payload, context)` right before posting and `finish()`es it with the outcome — status, duration, error, the raw body of an error response, and the response: the text as it arrived plus `finish_reason`, `usage`, generation `id` and `provider`, written however the stream ends, including an abandoned one. A Claude Code turn is one record too (`claude_code.run`). Records go to `data/requests/YYYY-MM-DD.jsonl` (UTC); ids are `YYYYMMDD-HHMMSS-<hex8>`, so an id names its day file and sorts in time. Base64 images inside a payload are stored once each, by SHA-256, in `data/requests/images/` and replaced in the logged payload by `logged-image:<file>`; everything else is the posted body verbatim (the API key is a header and never logged). A failure to log is logged and swallowed — it never breaks a call. Nothing is pruned automatically; delete old day files to free space. Callers pass `context={"mode": ..., ...}` (Conversar `{"mode": "conversation", "conversation_id", "step"}`); results carry `request_id` (`StreamEnd`) and failures raise `OpenRouterError` (a `RuntimeError` with `.request_id`). History entries keep the ids in `params.request_ids`; a Conversar message keeps its `request_id`, and the stream's error event includes it. `GET /api/requests` lists summaries newest-first (`limit`, `before` cursor = last id shown, `mode`, `errors`, plus `storage_bytes`), `GET /api/requests/{id}` returns the full record, `GET /api/requests/images/{file}` an image.

**MCP for agents** (`mcp_server.py`, the `mcp` SDK, pinned to 2.3.0: in 2.x `FastMCP` is `MCPServer`). Everything the frontend does, as MCP tools for external agents (the bot's personality as `get_personality`/`set_personality`), over streamable HTTP at `/mcp` (stateless, JSON responses). `main.py` calls `mcp_server.attach(app)` (a plain Starlette route, so the app's `require_auth` dependency doesn't cover it: `_Endpoint` checks the same Basic Auth itself) and enters `mcp_server.running()` in the lifespan (it builds the MCP HTTP app and runs its session manager, which can run only once -- hence a fresh one per lifespan; with the app not started, `/mcp` answers 503). DNS rebinding protection is off: the app is reached under whatever LAN address it has, and the credentials are the boundary. Every tool calls the app's own API in-process (`_call`: `httpx2`'s `ASGITransport`, httpx2 being the SDK's HTTP client), so checks, errors and side effects are the frontend's; an API error becomes a `ToolError` with its `detail`. Tools take families by name or id (`_family_id`, loosely matched: "krea-2" finds "Krea 2"), images as base64 (`_image_file`: PNG, JPEG or WebP, data URIs too, bytes untouched so embedded workflows survive), and an omitted model means the app's default. Conversations come back as `_conversation_view` (messages with the bot's prompts numbered and the base model each is for, images numbered with review and reaction, runs) instead of the raw file; `send_message`/`start_conversation` wait for the reply (the NDJSON stream, read whole), `wait_for_conversation` polls until nothing is under way (twice idle in a row: a finished run hands over to the bot's comment) and returns what arrived since the agent's last message, `get_image` returns the image itself. `start_conversation` deletes the conversation it created if its first message is refused before anything is stored. `finish_conversation` ends a conversation (`POST …/finish`: the bot's balance first, when runs made images), `get_balance_data` returns the evidence without asking the bot. Creating the `MCPServer` calls `logging.basicConfig`, which `_server()` undoes (the app logs once, through its own handlers). Tests (`tests/test_mcp.py`) speak JSON-RPC to `/mcp` through the test client inside its lifespan (`with api_client:`), with the run tracker's thread kept off.

**Conversar** (`routes/conversations.py`, `conversation_turn.py`, `chat.py`, `chat_tools.py`, `conversations.py`, `memory.py`). `chat.build_system_prompt` is the editable personality (the `conversation` system prompt, which is *only* the bot's character), the family rules (introduced by `FAMILY_RULES_INTRO`: they govern the text inside a block, not the shape of a reply, since families were written for one-shot prompts and say things like "output only the prompt"), and -- only when the bot can run ComfyUI workflows -- the workflow library (names, families, default sizes and descriptions), and **last** `CONVERSATION_MECHANICS` (+ `COMFY_MECHANICS` with ComfyUI), fixed in code and declared to take precedence over anything above, so neither the personality nor a family can break them: reply in the user's language with prompts in English, deliver each prompt as a `<prompt>POSITIVE: …\nNEGATIVE: …</prompt>` block, keep telegraphic notes and change them straight away without asking -- `<remember>…</remember>` adds one, `<remember id="n">…</remember>` rewrites note n, `<forget id="n"/>` deletes it (numbers are resolved against the notes as listed at the start of the turn) -- and, only while the conversation has no title, start with `<title>…</title>`. What changes from turn to turn is not in the system prompt (which then stays the same, and cached, the whole conversation) but in `chat.turn_context`, the last part of the latest message: the title request while there is none, every memory note **numbered** (`[1] …`), and the installed models with their stats (`catalog.prompt_section(covers=…)`: in full only for the conversation's family -- `families.covers_folder` --, the other families' base models by name and their LoRAs as a count; list_comfy_models has the rest). **Notes have a scope** (`memory.py`, lorebook-like): general (the user's tastes and way of working: every turn), a family's (`family`: a model folder, "krea-2": when the conversation's family covers it) or a topic's (`topic`: a character, series, project or theme: when the topic is active -- the conversation's `topics`, which the bot declares with `<topics>Kim</topics>` (`conversations.set_topics`; the chat's header shows them), or its name or a keyword (`topics.json`, edited in Ajustes) appears, as a whole word, accents and case aside, in the latest `SCAN_MESSAGES` messages or the title: `memory.active_topics`). `memory.notes_for_turn` sends what applies within `NOTES_BUDGET` characters (about 1,200 tokens) -- general, then the family's, then the topics', each group's most recently confirmed first -- numbered in group order and, within a group, oldest first (so numbers stay put), and names what was left out ("topic Ramona (12)") and the topics the notes have (`chat.notes_text`). The bot writes `<remember family="krea-2">`, `<remember topic="Kim">` or `<remember>` (general), moves one with `<remember id="n" topic="…">`, and `<confirm id="n"/>` when a note proved right again (`confirmations`, `confirmed_at`). Ajustes lists the notes by scope with what each group weighs and when it goes, and edits scopes and topics' keywords (`/api/admin/memory` with `scope`/`family`/`topic`, `/api/admin/memory/topics`). Notes without a scope are general. **Ordenar la memoria** (`memory_tidy.py`, Ajustes' button over the notes, `/api/admin/memory/tidy`, MCP `tidy_memory`/`apply_memory_tidy`): the bot reviews every note at once -- on Claude Code (`claude_code.ask`: a one-off `claude -p --output-format json`, no tools, no MCP, `--no-session-persistence`, the same account and lockdown) or an OpenRouter model -- and answers JSON operations (rewrite, split, merge, forget, move), each with its reason in Spanish; `_validate` keeps those whose notes exist, each used once, and whose results keep the rules (`chat.note_problem`, an existing family folder), counting the rest as dropped. The plan waits in `memory_tidy.json` (before and after of each operation) until the user applies the ones ticked (`apply`: written at once, keeping each note's date, conversation and confirmations -- a merge adds them up --, skipping any whose notes changed since) or discards it; what was there before goes to `memory_tidy_undo.json`, and "Deshacer el último orden" puts it back, with any note written since. **A note is one claim that stands on its own** in any conversation: at most `chat.NOTE_LIMIT` (240) characters and no image numbers (`chat.note_problem`); one that breaks that isn't kept -- never cut -- but stored on the reply as `notes_refused` (`{text, reason, id?}`; the chat shows it as "No guardada" with the reason), and the next turn's context tells the bot once (`chat.refused_notes_text`, from `_last_reply`) so it writes it again. `chat.build_llm_messages` replays the conversation: the bot's earlier blocks renumbered as `<prompt id="n">` so the user can refer to proposals by the number the UI shows (keeping a `model="…"` the bot gave the block: with ComfyUI, `COMFY_MECHANICS` has it name in each block the base model file the prompt is for, which `parse_reply` stores as the prompt part's `model`); every image numbered across the conversation ("Image 3:"), with the generation metadata it carries (`image_metadata.describe`), but only recent ones attached (their small copy) since every image is re-sent on every turn: the latest `CONTEXT_IMAGES_MIN` to `MIN + STEP - 1`, the window moving `CONTEXT_IMAGES_STEP` at a time so old messages don't change from turn to turn; a "results" message as a user turn ("[Run 2 (krea-2/txt2img, 2:3 portrait, 1 MP) finished: image 5 (seed …)]", marked automatic when nothing or the bot's reply follows it), merged with the user's next message; the user's reactions as "[Reactions: image 5 liked; image 6 disliked: "…"]"; and a reply made in steps as assistant `tool_calls` + `tool` results when the request carries tools (listing results from earlier turns elided, `KEPT_RESULTS` kept), or summarized in text when it doesn't (`_call_text`: a prompt a call runs named by its block's number, "(prompt 12)", not repeated; a run's images aren't labelled one by one when no longer attached -- its results line names them). **A long conversation is compacted** (`compacted_until`): once the part replayed in full passes `COMPACT_ABOVE` characters (80k, by `_replay_size`), the older messages go in brief, leaving about the latest `COMPACT_KEEP` (30k) and at least `COMPACT_MIN_MESSAGES` in full -- each of the bot's replies as its first words, each block's opening (`<prompt id="12">…</prompt>`, `PROMPT_GIST`) and its calls in brief (`_brief_reply`); the user's messages, results and reactions kept (long texts and images' metadata cut); `COMPACTED_NOTE` first. The boundary is decided message by message from the start, so it moves only now and then and stays put in between (the prompt cache is rewritten once per move); `get_prompt(number)` (a tool on OpenRouter, a lookup on Claude Code) gives an old block in full (`chat.prompt_by_number`). Ramona's conversation (212 messages) went from ~184k tokens to ~72k (2026-11-04). `chat.parse_reply` turns a reply's text into `content` (notes and title stripped, blocks kept: what the LLM sees next turn), ordered `parts` (`text` / `prompt`, via `prompts.parse_response`, so `has_negative_prompt` applies), `notes`, `note_updates`, `note_forgets` and `title`; an unclosed title or note ends at its line, an unclosed prompt block (a truncated reply) runs to the end. A reply with no blocks at all gets each bare `POSITIVE: …` paragraph (plus a `NEGATIVE: …` paragraph right after it) wrapped in a block first, so a model that slipped into the family's one-shot format still yields cards — and the stored content shows it the block format next turn.
- **A turn** (`conversation_turn.run_turn`) holds a per-conversation lock from reading the conversation to storing the reply, so turns never overlap and a run's results can't land before the reply that launched it. A turn the user asks for doesn't run inside the request: `start_turn` runs it in a thread of its own that publishes its events to a `LiveTurn` (registered per conversation while it lasts), and the request only follows it (`LiveTurn.follow`: every event from the first, plus `None` every `KEEPALIVE_SECONDS` of silence, sent as a blank line). So a reply goes on and is stored when the chat that asked switches conversation, reloads or closes; several conversations reply at once; and `GET …/live` lets any chat pick up a reply under way from its start. The automatic comment on results is a `LiveTurn` too. A message (or retry) while a turn is under way there, or the bot is about to comment, is refused with 409 (`is_busy`): it would land before the reply. It streams the reply; when ComfyUI is configured and the model takes tools (`toolbox_for`), the request carries `chat_tools.TOOLS` and the bot may call them: each call runs (`ToolBox.run` → `(result for the LLM, part for the chat)`; errors are results too, so the bot can fix its call), and the reply continues in a new request, up to `MAX_STEPS`, the last with `tool_choice: "none"` -- except after a step that launched a run (`run_workflow`, `calibrate_lora`) and called nothing else whose result the bot must read (only `QUIET_TOOLS`, none failed; a family switch comes back as an error): that ends the turn (`_launched`), since the next request would only be for the bot to say it launched -- `COMFY_MECHANICS` tells it to say what it runs before the call and to make every launch it announces in that same step (one call per run: "three variations" launched one at a time got one), and the call and its result are replayed next turn as they are. Its automatic look at a run's results has no tools, and the turn context says so (`chat.LOOKING_RULE`), so it proposes the next run instead of promising it. Each step is its own request-log entry (`context.step`). `_turn` prepares what both engines share (family, notes, toolbox, library, the turn context's parts) and then runs `_openrouter_steps` or `claude_code.run`; storing the reply is common.
- **Claude Code as the bot** (`claude_code.py`, `bot_seat.py`). A conversation's `engine` is `"openrouter"` (default) or `"claude-code"` (with `claude_model`: opus, sonnet, haiku, and `claude_effort`, passed as `--effort`: low, medium, high, xhigh, max, or "" for the model's own -- "Esfuerzo"; "Responde" in the chat's settings, offered when the CLI is installed, `claude_code.available()`). A Claude Code turn runs the CLI headless once: `claude -p`, stream-json in and out with partial messages, `--session-id` (a UUID the app picks) on the first turn and `--resume` after (the session id, the digests of the system prompt's changing sections at its start and of the context last sent are the conversation's `claude_code`, `conversations.set_claude_code`), in an empty folder (`data/claude-code/workspace`), with `CLAUDE_CONFIG_DIR` = `CLAUDE_CODE_CONFIG_DIR` (default `~/.claude-prompt-enhancer`: its own login, an account of its own, and none of the PC's other Claude Code settings, plugins, hooks or sessions; `ANTHROPIC_*`/`CLAUDE_CODE_*` variables kept out of its environment) and locked down: `--tools ""` (no built-in tools), `--strict-mcp-config --mcp-config` (one server: this app's `/mcp/bot/<token>`), `--allowedTools mcp__pe__*`, `--permission-mode dontAsk`, `--setting-sources ""`, `--settings` (sessions kept 3650 days, not 30), `--system-prompt-file`, `--max-turns`; a session whose init lists any other tool is killed (`_check_tools`). Never `--bare` (it ignores subscription logins) nor `--safe-mode` (it drops `--mcp-config`). Its system prompt is `chat.system_sections` -- the same personality (Ajustes' "Conversar", for both engines), family rules, library and mechanics -- plus `CLAUDE_CODE_MECHANICS` (tool names, proposal numbering, `get_image`, launching every announced run before ending). Claude Code records the system prompt when a session starts and keeps it, so a section that changed since (family, library, families) comes in the turn's message under `CHANGED_HEADING`, and the notes and installed models are sent again only when they changed or every `RESEND_EVERY` turns (`UNCHANGED_NOTE` otherwise): the session holds what came before. The message is the latest user-side message as `build_llm_messages` makes it (results, text, images, reactions, the context) as Claude content blocks; a session's first turn in a conversation that already has messages (begun on OpenRouter, or a lost session -- then retried once with a new one) gets the conversation so far first (`HISTORY_INTRO`). The turn context also tells it the numbers of its previous reply's blocks (its own session doesn't have the app's ids). Its tools are the bot's, served by `bot_seat.py` over MCP (a low-level `mcp.server.lowlevel.Server` with the `chat_tools.TOOLS` schemas, run by the same `ToolBox`, plus the lookups `get_image` and `get_balance_data`) at `/mcp/bot/<token>`: a `Seat` per turn (`open_seat`/`close_seat`), its token the credential (the route is outside the app's Basic Auth, and the log masks it), valid only for that conversation and while the turn lasts; `tools_allowed=False` on an automatic look or a balance refuses runs. A call coming in over HTTP waits until the turn's thread has read its `tool_use` (`Seat.saw_call`), so `ToolBox.reply_text` (the block's model, the title) is set and its card lands after the text before it; the turn then claims the result when it reads the `tool_result` (`Seat.claim`, matched by name and arguments) and publishes the part. Text deltas stream as `delta` events; assistant text blocks and the calls build `steps` like OpenRouter's (lookups left out, so the conversation still replays on OpenRouter), stored by `_store_reply` with `engine` and `claude_code` (model, the CLI's `total_cost_usd` as `estimated_cost`, turns, duration, the subscription's `rate_limit` windows) -- not in `cost`: the subscription pays. Failures say what to do (`NOT_LOGGED_IN` with the `claude auth login` command for that folder); a CLI that quits before reading the message (a broken pipe) reports what it printed and its exit code. - **Seeing the images well** (Claude Code; 2026-11-04: the bot had missed 9 of the 21 images the user disliked). The turn's own images go as the small copy (1568, what the model takes), not shrunk -- only the replay at a session's start is (`IMAGE_SIDE`, `_blocks(shrink=True)` in `_history`). **The independent check** (`image_check.py`): before the turn that first sees a run's images (results since the bot last spoke; calibrations aside), a one-off `claude_code.ask` -- blocks with images (stream-json in and out), no session, no conversation, not told what was asked -- inspects up to `MAX_IMAGES` (12) with a retoucher's checklist (`SYSTEM`: fingers counted, limbs, joints, faces, continuity, background, rendering; "most have a flaw, report only what you see") and answers JSON (verdict, issues: what/where in Spanish, minor/major), kept to what holds (`_parsed`) and stored on each image as `check` (so a retry or redo doesn't pay again; one it didn't answer is "unknown"); the turn's context gets it (`context_text`, `CONTEXT_HEADING`: weigh it, it can be wrong, confirm by zooming), and the chat shows it under each image ("Revisión: …", red when major). A failure is logged and skipped. The conversation's `image_check` (default on; "Revisión independiente de las imágenes", shown for Claude Code) turns it off. **Off app-wide since 2026-11-05** (`image_check.ACTIVE = False`: nothing is inspected or sent to the bot, the setting and the findings under images are hidden, `data-image-check` on the chat's layout): over its first 87 images (26 requests on Opus, about $1.60 at API prices) it found something in 52 of the 54 it answered for, so it didn't tell good images from bad; its "major" findings fell on 4 images the user liked and 1 they disliked; 9 requests came back with nothing usable (every image "unknown", one conversation's every time); and half the reasons the user disliked an image (composition, style, not what was asked) are beyond a defect check. Its lessons, and what to try before turning it on again, are in Claude Code's memory for this project. The zoom stays, and so do the turn's images at full size; `CLAUDE_CODE_MECHANICS` no longer mentions the check (put it back with it). **Zooming in**: `get_image(number, regions)` (bot_seat) returns each region -- percent of width and height from the top left -- cropped from the original, at least `ZOOM_MIN_SIDE` (768) and at most `ZOOM_MAX_SIDE` a side (`_zoomed`); `CLAUDE_CODE_MECHANICS` asks for zooms on hands, faces and what the check flagged in the images that matter, all in one go.
- **Ending a conversation, and taking stock** (`balance.py`, the chat's "Terminar conversación"). Learning run by run is short-sighted: the bot sees the latest images only, its old reviews aren't replayed to it, and a note taken after one image is rarely revisited; so a conversation ends with a look back over all of it. `POST …/finish` (form field `focus`, optional) marks the conversation `finished_at` (the list says "Terminada"; the chat, "Conversación terminada"; any later user message reopens it, `conversations.append_message`) and, when its runs made images, appends a user message whose `balance` is the evidence the app builds from what is stored (`balance.ledger`): every image the runs made, grouped by run with its recipe -- workflow, the proposal whose prompt it ran (`proposal_numbers`, numbered as the bot sees them), base model, LoRAs and weights, sampler settings from the workflow sent (`run-<n>.json`, `Graph.generation_info`), size, seed; settings the same as the run before are said to be, not repeated -- with the user's reaction and the bot's review, then counts per ingredient (liked, disliked, unrated, flawed); plus what to do with it (`INSTRUCTIONS`: what worked best and worst with how many images back each point, the best recipe, what's untested, the user's judgment above its reviews, and its notes rewritten, merged or forgotten to match, a hunch noted only as one). It is stored on the message as sent, and replayed in full only while it waits for the bot's balance (that turn, or its retry): once answered, `build_llm_messages` replays one line instead (`balance.answered_text`, from `balance_counts`), since the balance follows anyway and the evidence would otherwise ride along every later turn -- the turn after a balance re-writes the cache from that message on, once. Claude Code keeps the evidence in its session. `balance_counts` keeps the totals for the chat. The turn carries the tools with `tool_choice: "none"` (`taking_stock` in `_turn`). Refused (409) while the bot works on its own; with no run images the conversation is only marked (JSON answer, no turn). `GET /api/conversations/{id}` gives such a message's `balance` as `true` (the text is tens of KB, and the chat re-reads the conversation while runs are under way); `GET …/balance` returns the evidence alone (`text` and the totals), for agents too. The chat's button sits in the header of any conversation under way; a first press asks to confirm, saying how many images are still unrated.
- **Isolation** (`comfy_policy.py`). The bot may only work with what the user gave it (library workflows, workflows embedded in images shared in the conversation) and what it made (its runs). Every workflow is checked before it is sent, and before `save_workflow` stores one: node types must come from the library, from workflows the user shared in this conversation, or `ALWAYS_ALLOWED` (core nodes that load nothing but model files), and never from `NEVER_ALLOWED` (nodes that read ComfyUI's folders, paths or URLs, like `LoadImageOutput`); any short string that looks like a file, path or URL must be one of this conversation's uploads (`input/prompt-enhancer/<conversation id>-<image id>.<ext>`). A saved workflow can't widen the allowed types (it is checked against them). `comfy.Comfy` itself only reads back what the app made: `view()` refuses anything but `output/prompt-enhancer/…` and the previews listed in its own jobs' `/history`, uploads go to `input/prompt-enhancer/`, model listings only for model folders, node definitions reach the bot only through `describe_nodes` (allowed types, file lists dropped), and nothing ever lists ComfyUI's queue or history (other projects' prompts and images live there).
- **Civitai** (`civitai.py`). A link to a Civitai image in a user message (`civitai.com/images/<id>`, also `civitai.green` and `civitai.red`, the same site; up to 4 images per message counting attachments) makes the app -- never the bot, which can't fetch anything -- read the image's record from Civitai's API (`/images?imageId=…&withMeta=true&nsfw=X`, with `CIVITAI_API_KEY` if set, which never goes to the image host), download the image and resolve the resources it was made with (`/model-versions/{id}` or `/by-hash/{hash}`: name, version, base model, trigger words, file, weight). It joins the message like an attached image, with that as its metadata (`source`, `resources`) and, if it was made with ComfyUI, its workflow (runnable as `image:N`). Any failure refuses the message with the reason (400), storing nothing.
- **Downloads from Civitai** (`downloads.py`; on with `COMFY_MODELS_DIR`, ComfyUI's models folder -- here `C:\comfy-ui\models`, its default in `extra_model_paths.yaml`). The app's own implementation (not ComfyUI-LoRA-Manager, which the owner doesn't want to depend on). The bot prepares, the user decides: `prepare_download(version_id | url | hash)` (`COMFY_MECHANICS`: when something the conversation needs isn't installed and Civitai has it -- a shared Civitai image's resource, whose text now gives its "Civitai version N"; a Civitai model link; a reference image's A1111 hash, which the study gives for what isn't installed) resolves the version (`civitai._get_json`), takes its SafeTensors file only (pickle formats can run code), places it -- models folder by type (LoRA, LoCon, LyCORIS, DoRA: `loras`; Checkpoint: `checkpoints`, or `diffusion_models` when the family has a folder only there) and family folder by Civitai's base model (`_family`: an existing folder whose name matches, or `BASE_FOLDERS`; else the user picks) -- and names it in the owner's convention (`file_name`: LoRAs "<category>-<name>_v<version>", the category from the model's Civitai tags -- char, style, concept, clothing, action, base, assets; checkpoints "<name>_v<version>"; base-model and format words dropped from the name), refusing what looks installed already (`catalog.match_installed`). It is stored on the conversation's `downloads` (`{n, version_id, model_name, version_name, model_type, base_model, size_bytes, sha256, folder, family, name, status: proposed|downloading|done|failed|declined|cancelled, installed_as, error, told}`), and the reply gets a `download` part: a card in the chat with what it is, its size, and the folder, family and name as editable fields, "Descargar" and "Descartar". Nothing is fetched until `POST …/downloads/{n}/accept` (`{folder, family, name}`): the target must be an existing family folder, a plain lowercase name, inside the models folder, not an existing file, with room to spare; then a thread (one download at a time) streams `https://civitai.com/api/download/models/<version>?type=Model&format=SafeTensor` (the API key as a header, which requests drops on the redirect to the file's host) into a `.part` file, checks the SafeTensors header and Civitai's SHA256, and renames it; progress is in memory (`progress`, merged into `GET` the conversation; the chat polls while one runs; "Cancelar" is `POST …/cancel`), and the catalog's file list is refreshed when it lands. `…/decline` turns one down. A restart marks one under way failed and deletes its `.part` (`after_restart`, in `lifespan`); a failed or cancelled one can be accepted again. The next turn's context tells the bot what became of each since it last heard (`news_text`, marked `told` once the reply is stored). `GET /api/model-folders` lists the family folders.
- **Reference folders** (`references.py`, Ajustes' "Carpetas de referencia", `/api/admin/reference-folders`). Folders of images on this PC the user accepted (`data/reference_folders.json`: name, absolute path; the path must exist; names unique, no `@`), for style and prompt writing. A user message that names one -- `@name` (the longest name that fits; typing `@` in the composer offers them, from the page's `reference_folders`) or its path pasted, or the path of a folder inside it (`find_mention`, `_deepest`: ".." can't leave it) -- makes the app, never the bot, read it and attach a study to that message (`study`): images only (PNG, JPEG, WebP; links leading out of the folder skipped; at most `MAX_LISTED` looked at, `MAX_STUDIED` read, spread evenly), their metadata read from the file's header (`image_metadata.read` takes a path), and the text the bot gets -- what to do with it (`INSTRUCTIONS`: what recurs is what works, since the user picked them; subject, style, recipe, how prompts are written; how many images back each point; notes named after the folder; nothing launched unless asked), the base models and LoRAs (weights' median and range, installed or not, `catalog.match_installed`), sampler settings and proportions that recur, the prompt phrases that recur (`phrases`: split at commas, lines and full stops, weights and LoRA tags dropped), a few whole prompts chosen to differ (`_pick_samples`), and a legend of contact sheets: JPEGs of numbered thumbnails (R1, R2...; `contact_sheets`, up to `MAX_SHEETS` of 16) stored as the message's images (`sheet: true`). The message keeps `references` (counts: name, path, images, studied, with_metadata, sheets; the chat shows them under it) and `reference_study` (the text, sent in full while it waits for the bot's answer, as one line after: `answered_text`, like the balance; `GET` gives it as `true`). A folder that can't be studied (gone, no images) refuses the message (400). Nothing is ever written in a folder; removing one from the list touches nothing in it. MCP: `list_reference_folders`, `add_reference_folder`, `remove_reference_folder`.
- **Images** (`image_metadata.py`, Pillow). `conversations.save_image` stores the bytes as received, a `-small.jpg` copy when the image is large (what the LLM and the thumbnails get), and for a shared image its generation metadata (`image_metadata.read`: ComfyUI's PNG `prompt` chunk or EXIF `prompt:`, A1111-style `parameters` in PNG or EXIF UserComment) on the image record, with the embedded API workflow apart as `<id>.workflow.json`. Only picked or dropped files keep metadata; a pasted image has been re-encoded without it. **Reactions**: `PUT /api/conversations/{id}/images/{image_id}/reaction` (`{rating: "up"|"love"|"down"|null, comment, reasons}`) stores one on the image, unsent -- "love" is a favorite ("es justo lo que busco"), the strongest like: it counts as liked and as loved in the catalog's stats ("2 liked (1 a favorite)") and the balance, and the bot is told to focus on it; a "down" needs `reasons` (`conversations.REACTION_REASONS`: hands, face, anatomy, style, composition, not_asked -- the chat's chips under a pressed thumbs down, one tap each) and/or a comment, and the stats count them per file ("1 disliked (hands 1)"); the user's next message takes every unsent reaction (`conversations.append_message` moves them to the message's `reactions`), and a message may be just that.
- `POST /api/conversations` creates one (family, model, temperature, character ids, `auto_comment`); `GET`/`PATCH`/`DELETE /api/conversations/{id}` read it (plus `replying` / `commenting`: the bot is answering, or commenting on results, right now), change its settings or its title (the user's: the bot only titles an untitled conversation; neither moves `updated_at`), delete it with its images (a reply under way there then fails to store); `GET /api/conversations` lists summaries (title falling back to the first message; `last_reply_at`, the last assistant or results message, for the chat's "new reply" mark; `running`, a run pending; and `replying`/`commenting`), most recently updated first.
- `POST /api/conversations/{id}/messages` (multipart: `content` plus up to 4 `images`, all validated before any is stored; content may be empty when there are unsent reactions) appends the user message and returns a `StreamingResponse` of NDJSON events: `{"type": "delta", "text"}` while the reply arrives, `{"type": "tool", "part"}` for each tool call, then `{"type": "done", "message", "conversation"}` once it is stored, or `{"type": "error", "detail", "request_id"}` — by then the status is already 200, so failures travel as events. Only a finished reply is stored (or, if a later step fails after tools ran, what was done, with `error`). A failed reply leaves the user (or results) message last; `POST /api/conversations/{id}/reply` answers it again (409 if it already has a reply). `GET …/live` streams the reply being written there, from its start, with the same events (204 when there is none). `POST …/redo` ("Rehacer la respuesta", under the bot's last reply while it is idle and no task it was given is running) discards that reply and has the bot answer again (`conversations.discard_last_reply`, which counts `redo` on the message answered, so the turn context tells the bot, `chat.REDO_RULE`, to answer differently): the runs it launched that are still pending are marked `discarded` and cancelled (their images never come into the chat, `on_run_finished`), the notes it took are forgotten and those it rewrote or forgot restored, its history entry deleted, and the budget between messages starts again; on Claude Code its session keeps the discarded reply, and the same rule says it was discarded. The chat asks for a second press when that cancels runs or undoes notes. `POST …/runs/{n}/cancel` cancels a pending run; `GET …/runs/{n}/workflow?job=` downloads the exact workflow sent; `GET …/images/{image_id}?small=true` serves the small copy.

**`routes/admin.py`** is a thin CRUD layer with no logic of its own — every endpoint is a one-line pass-through to `families`/`memory`/`system_prompt` functions, translating `None`/`False` returns from those modules into 404s (`/api/admin/memory` is the bot's notes; Conversar's "Olvidar" and "Deshacer" go through it too), and `workflows.WorkflowError` into 400s. Besides those: `/api/admin/workflows` (the library; `POST …/extract` reads the workflow out of a ComfyUI image) and `/api/admin/catalog` (`GET`, `POST …/refresh` -- synchronous, reads ComfyUI --, `PUT …/description {file, text}`). System-prompt endpoints are parameterized by `mode`, validated against `VALID_SYSTEM_PROMPT_MODES` (the keys of `seed.DEFAULT_SYSTEM_PROMPTS`: only `conversation` now; the old modes answer 400); `GET /api/admin/system-prompt/{mode}/default` returns the seed text so Ajustes can offer "Cargar el texto original" without overwriting anything. `routes/pages.py` only renders templates: `/` redirects to `/conversar`, which gets the families, the default model, whether ComfyUI is configured and whether Claude Code is installed (with its models); historial and admin fetch their own data client-side.

**Frontend.** One Jinja2 template + one ES-module script per page (Conversar, Historial, Ajustes, Peticiones), plus `static/common.js`, the one shared module: `request()` (fetch with timeout, JSON or FormData body, throws an `Error` carrying the server's `detail`), the `el()` DOM builder, `copyButton`, `setBusy`, the two-step `confirmButton` (no `window.confirm`), `toast`, the floating cost popup, and `renderTake(entry, handlers)` — the card that renders one history entry in Historial (header, brief, "Abrir la conversación" for Conversar entries, the reference prompts an old Variaciones request started from, warnings, numbered frames with Copiar/Iterar); a handler left out hides its action. `frameBody` (one prompt's text, negative and actions) is shared with Conversar's proposals, and `startConversationFrom(entry, prompt)` is what "Iterar" does: stash the prompt and settings in `sessionStorage["conversation-start"]` and go to `/conversar`, which opens a new conversation with "Partamos de este prompt: …" in the message box. The visual language (darkroom palette, the Archivo variable font served from `static/fonts/`, amber frame numbers) lives entirely in `style.css` tokens.
- `historial.html`/`historial.js`: client-side search (ideas, prompts, aesthetics, the references and the character names old entries carry), mode/family/favorites filters, 25 entries per page, total cost of the filtered set. "Iterar" opens a conversation from the prompt (`startConversationFrom`).
- `conversar.html`/`conversar.js` ("Conversar"): clicking an image opens the viewer (a `<dialog>` over the page, all the conversation's images browsable with the arrow keys; ctrl-click still opens a tab). Conversation list on the left (a drawer below 900px), the chat on the right with a settings panel (family, who answers -- a model on OpenRouter, with its temperature, or Claude Code with its model --, and with ComfyUI whether the bot comments on a run's images when they arrive: kept in `state.draft` until the first message creates the conversation, `PATCH`ed after; the last ones used persist in `localStorage["conversation-settings"]`). Several conversations can be replying at once, and switching never waits: each reply under way is a `follow()` (one per conversation, in `state.live`) that reads its NDJSON stream with `fetch` + a body reader -- the POST that sent the message, or `GET …/live` to pick up one the chat didn't ask for (`attachIfReplying`: after a reload, in another tab, the bot's comment on results) -- keeps what arrived, and draws it only while its conversation is open; `liveParts()` (a JS mirror of `chat.parse_reply`, minus the bare-prompt fallback, which shows once the reply is stored) renders the partial reply, and the stored message replaces it on `done` (`settle`). The stream has an idle timeout (`STREAM_IDLE_MS`; the server's blank lines keep it alive); a cut connection doesn't end the reply, which is picked up again from the server. A request refused before anything was stored (`Rejected`) puts the text and images back in the composer (or in that conversation's draft, with a toast, if it isn't open); a failed reply leaves "Reintentar" with its reason (as does a conversation whose last message has no reply). The composer's text and attachments stay with their conversation when switching (`state.drafts`), and the send button is busy only in a conversation whose bot is at work. The list shows per conversation "Respondiendo…"/"Comentando…"/"Generando imágenes…", or "Respuesta nueva" (a dot) when something arrived since it was last open (`last_reply_at` against `localStorage["conversation-seen"]`) -- and when what arrived are run images, the images themselves: "3 imágenes nuevas" and a strip of the newest `LIST_THUMBS` (4) thumbnails with "+N" under the conversation (`unseenImages`, from the summary's `recent_images`: its newest `conversations.RECENT_IMAGES` (30) run images with their results message's timestamp; new images being the main reason to open a conversation that is generating), re-reading itself every `LIST_POLL_MS` while another conversation has something under way; each row renames (the title becomes a field: Intro or leaving saves, Escape drops) and deletes (two-step) on hover or focus, always on the open one. Proposals are numbered across the whole conversation, matching the ids the LLM sees, show under their first line the base model they are for (`proposalModels`: the `base_models` of the runs launched with the same positive prompt, ignoring spacing and case -- since runs load the model their block names, the same one -- or else the model the bot named in the block), and fold to one line -- number, the start of the prompt, the model -- with "Copiar" at hand (`proposal()`; the full frame body, shared with `renderFrame` as `common.frameBody`, when unfolded; which ones are unfolded is kept for the session); a reply's proposals in a row share one list (`fillBotMessage`: a reply proposes its prompts one after another and then launches their runs, so a card apiece took most of the chat). The bot's text goes through a small Markdown subset built as DOM nodes (no `innerHTML`). Each note the bot took shows as a chip with "Olvidar"; notes already gone from memory render as forgotten; a note it rewrote or forgot shows with "Deshacer" (restore the previous text, or recreate it). Images can be picked, pasted or dropped (4 per message); sending them to a model the model list marks as text-only is blocked. Every image shows its number (the one the bot sees); a shared image with metadata gets a collapsible panel with it. While streaming, `tool` events split the reply into segments, and the runs the bot launched one after another show as one line (`runGroup`: "Ejecuciones 12–14 · krea-2/txt2img, 9 imágenes · En cola o generando", or what became of each, with the images they made; "Pasar delante" for those still waiting) that updates as they go and unfolds to each run (status, error, Cancelar, the workflow sent, and the conversation's ComfyUI folder: rarely needed, since the images come below); a results message is a contact sheet whose frames each have thumbs up/down and a comment (`PUT …/reaction`), and the composer says how many reactions will go with the next message (which may then be empty). While a run is pending or the bot is commenting on results, `schedulePoll()` re-reads the conversation every `POLL_MS` (only with the tab visible, not mid-typing a comment) and redraws what changed. The settings panel says whether the bot can run workflows with the chosen model (`supports_tools`).
