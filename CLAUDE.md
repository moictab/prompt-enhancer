# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```
pip install -e ".[dev]"          # install app + dev deps (pytest, httpx) from pyproject.toml
pytest                           # run the full test suite
pytest tests/test_prompts.py     # run a single test file
pytest tests/test_prompts.py::test_parse_response_splits_positive_and_negative  # run a single test
uvicorn app.main:app --reload    # run the dev server at http://localhost:8000
docker compose up --build        # build and run the containerized app (reads .env, mounts ./data)
```

Copy `.env.example` to `.env` before running anything — `OPENROUTER_API_KEY`, `ADMIN_USERNAME`, `ADMIN_PASSWORD` (plus optional `DEFAULT_LLM_MODEL`/`DEFAULT_VISION_MODEL`, the models prefilled in the UI, and `COMFY_GATEWAY_URL`/`COMFY_DIRECT_URL`, which let Conversar's bot run ComfyUI workflows; unset, that whole part is off). `tests/conftest.py` unsets the ComfyUI variables for every test; tests that need ComfyUI use the `fake_comfy` fixture (a `FakeComfy` standing in for `comfy.Comfy`), and `png_bytes(**texts)` makes real PNGs with text chunks. The app refuses to start (raises in `lifespan`) if `ADMIN_PASSWORD` is unset, so tests set all three via `monkeypatch.setenv` in `tests/conftest.py`'s `api_client` fixture rather than relying on a `.env` file.

## Architecture

FastAPI + Jinja2 + vanilla JS. No build step (no bundler, no npm), no database — every persistent thing is a flat JSON or JSONL file under `data/` (gitignored, Docker-volume-mounted). `app/storage.py` is the only place that touches the filesystem for JSON: `read_json`/`write_json` (atomic via tempfile + `os.replace`) for families/characters/system prompts, `append_jsonl`/`read_jsonl`/`write_jsonl` (atomic rewrite) for history, plus `write_bytes`/`remove` for the images shared in Conversar. Every domain module (`families.py`, `characters.py`, `history.py`, `system_prompt.py`, `memory.py`) follows the same shape: a `_default_path()` derived from `get_settings().data_dir`, plain functions that accept an optional `path` override (this is how tests get isolation — `tests/conftest.py` sets `DATA_DIR` to `tmp_path` per test rather than every module needing a path argument at the call site), and no classes/ORM — just lists/dicts of plain data read-modify-written wholesale on every mutation. `workflows.py` (`data/workflows.json`, the ComfyUI workflow library, seeded once from `app/seed_workflows/` -- the owner's workflows, taken from the sibling image-generation project -- when the file doesn't exist) and `catalog.py` (`data/catalog.json`) follow it too. The exception is `conversations.py`: a conversation grows with every message, so each one is its own `data/conversations/<id>.json` (images in `data/conversations/<id>/`, each with a `-small.jpg` copy when large and a `.workflow.json` when it embeds a ComfyUI workflow, plus `run-<n>.json`, the workflows sent for run n), read-modify-written under a lock; ids are validated as UUIDs before they touch a path, and functions take an optional `root` folder override instead of `path`. `request_log.py` (below) is the other one: a JSONL file per day plus an image folder. Because every OpenRouter call now writes to disk, `tests/conftest.py` points `DATA_DIR` at `tmp_path` for every test (autouse), not only for `api_client`.

**Request flow.** `app/main.py` wires a single FastAPI app with a global `Depends(require_auth)` dependency, so *every* route (including static files and page routes) is behind HTTP Basic Auth — there's no per-route auth annotation to forget. `app/auth.py` compares credentials with `secrets.compare_digest` against `Settings.admin_username/admin_password`. A middleware in `main.py` logs method/path/status/duration for every request and sets `Cache-Control: no-cache` on `/static/*` (no hashed filenames, so browsers must revalidate after a deploy); `main.py` also pins `.js` to `text/javascript`, since the frontend is ES modules and Windows can map `.js` to `text/plain`. On startup, `lifespan()` calls `seed.ensure_seed_data(data_dir)`, which creates `families.json` (seeded with SDXL and Z-Image-Turbo, each with hardcoded `*_INSTRUCTIONS` text) and an empty `characters.json` only if those files don't exist, and fills `system_prompts.json` **per mode** from `seed.DEFAULT_SYSTEM_PROMPTS` (`generate`, `image`, `story`, `variations`, `conversation`, `extract_character`): modes missing from the file are added, modes already present (edited or not) are never touched — so adding a new mode reaches existing deployments, and changing a default does not (deployments seeded earlier keep their text until someone loads the original in Ajustes). The retired one-shot refine left an unused `iterate` key in older deployments' files; nothing reads it.

**`routes/api.py`** is where generation actually happens. Every prompt-crafting endpoint runs the same pipeline through shared helpers: `_require_family` (404 if unknown) → `prompts.build_system_prompt(mode, family)` (that mode's prompt from `data/system_prompts.json` + the family's instructions) → `prompts.build_user_message(mode, ...)` (where selected `character_ids` are resolved and inlined verbatim; every section heading and instruction it writes is in English, like the seeded system prompts, since the prompts themselves are English -- only the UI is Spanish, so e.g. the Variaciones axes have Spanish UI labels in `VARIATION_AXES` and English names for the LLM in `VARIATION_AXIS_NAMES`) → `_call_llm(label, model, system, user_messages, ...)` → parse → `_record(...)`, which appends the history entry and returns **the history entry itself plus `truncated` and `count_mismatch`**. So all of them respond with the same shape — `{id, timestamp, mode, family_id, family_name, llm_model, vision_model, temperature, user_input, example_prompts, previous_prompt, prompts: [{positive_prompt, negative_prompt}], cost, params, favorite, truncated, count_mismatch}` — and the frontend renders a fresh response and a history entry with the same code.
- `POST /api/generate` turns an idea into a prompt (it used to also refine one given as `previous_prompt`, the "iterate" mode; that moved to Conversar, and history entries with `mode: "iterate"` remain from before). `POST /api/from-image` is the vision ("image") mode. Both take `variants` (1–4): `_call_llm` makes one OpenRouter call per variant **in parallel** (`ThreadPoolExecutor`), each user message tagged with an `## Alternative` section (`variant=(i, n)`) nudging it toward its own interpretation, each parsed with `prompts.parse_response`. A failed variant is dropped (and `count_mismatch` is set); only if every call fails does the request 502. `cost` is the sum.
- `POST /api/story` (2–12 episodes) and `POST /api/variations` (2–12 variations) make a **single** call whose response holds one `POSITIVE:`/`NEGATIVE:` block per prompt, split by `prompts.parse_multi_response`; `count_mismatch` flags a different number of blocks than requested. Variaciones holds characters, an `aesthetic` and an optional base idea constant and takes `axes: [{key, vary, value}]` over `prompts.VARIATION_AXES` (outfit, setting, lighting, pose, camera, expression): a fixed axis repeats `value` (or one model-chosen option) in every prompt, a varying axis must differ across prompts (staying within `value` as hints). It also takes up to 12 `reference_prompts` (prompts the user already likes, usually of the same subject; blanks dropped): `build_user_message` puts them first under `## Reference Prompts`, numbered, with the instructions for using them (keep what they share as the constant subject, take the best of each, the rest of the request and the family rules win) -- in the user message rather than the system prompt, so existing deployments get them without reseeding. It 400s if no axis varies or nothing is held constant (references count as constant). Axis labels, and the references when given, are stored in the entry's `params` so history stays readable.
- `POST /api/extract-character` and `POST /api/extract-character-from-image` are a separate, simpler flow: the fixed `extract_character` system prompt, a `NAME:`/`TEXT:` response parsed by `prompts.parse_character_response`, returning `{name, text, cost, truncated}` for the caller to save via `POST /api/admin/characters`. Neither writes to history.
- `GET /api/history` returns entries newest-first; `PATCH /api/history/{id}` (`{favorite}`) and `DELETE /api/history/{id}` rewrite the JSONL under a lock in `history.py`. Entries written before the `prompts` list existed (a top-level `positive_prompt`/`negative_prompt`, or a story's `episodes`) are normalized on read by `history._normalize`, and migrated on disk the first time any entry is favorited or deleted.

`GET /api/openrouter-models` proxies OpenRouter's model list (`openrouter_client.list_models()`, in-process cached for `MODELS_CACHE_TTL_SECONDS`), annotating each with `supports_images` so the frontend can filter which models are offered for vision modes.

`has_negative_prompt` (set per-family in `families.json`/Ajustes) is the single flag that drives negative-prompt suppression: `prompts.parse_response`/`parse_multi_response` always parse out whatever the LLM put after `NEGATIVE:`, but force it to `""` when the family says it doesn't use one (e.g. Z-Image-Turbo, whose instructions also tell the LLM not to bother generating one — the code-level suppression is the actual guarantee, not the prompt wording). The frontend hides the negative block when it's empty.

`openrouter_client.call_openrouter` retries once (`max_attempts = 2`) when OpenRouter returns a response whose `content` is missing or not a string (a malformed-response class seen in practice, distinct from HTTP-level errors which raise immediately as `RuntimeError` with a user-facing message). `max_tokens` is 8192 and the request timeout is 180 s (a 12-prompt story or variation set takes a while and arrives in one piece); the frontend's own fetch timeout in `common.js` is set above that. Every response's `usage.cost` is threaded back through as `OpenRouterResult.cost`. `OpenRouterResult.truncated` mirrors `choices[0].finish_reason == "length"` — not retried, just surfaced so the UI can warn that a prompt may be incomplete. `openrouter_client.stream_chat(api_key, model, messages, temperature, context, tools, tool_choice)` is the streamed counterpart Conversar uses: it takes a full chat `messages` list, reads OpenRouter's server-sent events and yields each text delta, then one `StreamEnd(cost, truncated, request_id, tool_calls)` -- with `tools` (OpenAI-style function definitions) the model may call them, and the calls, which arrive in pieces, come back assembled as `[{id, name, arguments}]`; it shares the HTTP error mapping with `call_openrouter` but never retries (part of the reply may already be on screen), and raises `RuntimeError` for an error reported mid-stream or a dropped connection. `list_models()` also annotates `supports_tools` (from `supported_parameters`). Both calls send `provider: PROVIDER_PREFERENCES` (`{"data_collection": "deny"}`): OpenRouter only routes to providers that neither store nor train on the data, since prompts and images are personal; a model with no such provider fails with an explained 404.

**Request log** (`request_log.py`, `routes/requests.py`, the Peticiones page). Every HTTP request to OpenRouter is recorded *as sent*, not reconstructed: both client functions open a `RequestRecord(payload, context)` right before posting and `finish()` it with the outcome — status, duration, error, the raw body of an error response, and the response (the full JSON for `call_openrouter`; for `stream_chat`, the text as it arrived plus `finish_reason`, `usage`, generation `id` and `provider`, written however the stream ends, including an abandoned one). Each retry attempt is its own record. Records go to `data/requests/YYYY-MM-DD.jsonl` (UTC); ids are `YYYYMMDD-HHMMSS-<hex8>`, so an id names its day file and sorts in time. Base64 images inside a payload are stored once each, by SHA-256, in `data/requests/images/` and replaced in the logged payload by `logged-image:<file>`; everything else is the posted body verbatim (the API key is a header and never logged). A failure to log is logged and swallowed — it never breaks a call. Nothing is pruned automatically; delete old day files to free space. Callers pass `context={"mode": ..., ...}` (`_call_llm` its label, Conversar `{"mode": "conversation", "conversation_id"}`); results carry `request_id` (`OpenRouterResult`, `StreamEnd`) and failures raise `OpenRouterError` (a `RuntimeError` with `.request_id`). `_record` stores the ids in the history entry's `params.request_ids`; a Conversar message keeps its `request_id`, and the stream's error event includes it. `GET /api/requests` lists summaries newest-first (`limit`, `before` cursor = last id shown, `mode`, `errors`, plus `storage_bytes`), `GET /api/requests/{id}` returns the full record, `GET /api/requests/images/{file}` an image.

**Conversar** (`routes/conversations.py`, `conversation_turn.py`, `chat.py`, `chat_tools.py`, `conversations.py`, `memory.py`). `chat.build_system_prompt` is the editable personality (the `conversation` system prompt, which is *only* the bot's character), the family rules (introduced by `FAMILY_RULES_INTRO`: they govern the text inside a block, not the shape of a reply, since families are written for the one-shot modes and say things like "output only the prompt"), the selected characters, every memory note **numbered** (`[1] …`), and -- only when the bot can run ComfyUI workflows -- the workflow library (names and descriptions) and the installed models (`catalog.prompt_section()`), and **last** `CONVERSATION_MECHANICS` (+ `COMFY_MECHANICS` with ComfyUI), fixed in code and declared to take precedence over anything above, so neither the personality nor a family can break them: reply in the user's language with prompts in English, deliver each prompt as a `<prompt>POSITIVE: …\nNEGATIVE: …</prompt>` block, keep telegraphic notes and change them straight away without asking -- `<remember>…</remember>` adds one, `<remember id="n">…</remember>` rewrites note n, `<forget id="n"/>` deletes it (numbers are resolved against the notes as listed at the start of the turn) -- and, only while the conversation has no title, start with `<title>…</title>`. `chat.build_llm_messages` replays the conversation: the bot's earlier blocks renumbered as `<prompt id="n">` so the user can refer to proposals by the number the UI shows; every image numbered across the conversation ("Image 3:"), with the generation metadata it carries (`image_metadata.describe`), but only the `MAX_CONTEXT_IMAGES` most recent attached (their small copy) since every image is re-sent on every turn; a "results" message as a user turn ("[Run 2 (krea-2/txt2img) finished: image 5 (seed …)]", marked automatic when nothing follows it), merged with the user's next message; the user's reactions as "[Reactions: image 5 liked; image 6 disliked: "…"]"; and a reply made in steps as assistant `tool_calls` + `tool` results when the request carries tools (listing results from earlier turns elided, `KEPT_RESULTS` kept), or summarized in text when it doesn't. `chat.parse_reply` turns a reply's text into `content` (notes and title stripped, blocks kept: what the LLM sees next turn), ordered `parts` (`text` / `prompt`, via `prompts.parse_response`, so `has_negative_prompt` applies), `notes`, `note_updates`, `note_forgets` and `title`; an unclosed title or note ends at its line, an unclosed prompt block (a truncated reply) runs to the end. A reply with no blocks at all gets each bare `POSITIVE: …` paragraph (plus a `NEGATIVE: …` paragraph right after it) wrapped in a block first, so a model that slipped into the family's one-shot format still yields cards — and the stored content shows it the block format next turn.
- **A turn** (`conversation_turn.run_turn`) holds a per-conversation lock from reading the conversation to storing the reply, so turns never overlap and a run's results can't land before the reply that launched it. A turn the user asks for doesn't run inside the request: `start_turn` runs it in a thread of its own that publishes its events to a `LiveTurn` (registered per conversation while it lasts), and the request only follows it (`LiveTurn.follow`: every event from the first, plus `None` every `KEEPALIVE_SECONDS` of silence, sent as a blank line). So a reply goes on and is stored when the chat that asked switches conversation, reloads or closes; several conversations reply at once; and `GET …/live` lets any chat pick up a reply under way from its start. The automatic comment on results is a `LiveTurn` too. A message (or retry) while a turn is under way there, or the bot is about to comment, is refused with 409 (`is_busy`): it would land before the reply. It streams the reply; when ComfyUI is configured and the model takes tools (`toolbox_for`), the request carries `chat_tools.TOOLS` and the bot may call them: each call runs (`ToolBox.run` → `(result for the LLM, part for the chat)`; errors are results too, so the bot can fix its call), and the reply continues in a new request, up to `MAX_STEPS`, the last with `tool_choice: "none"`. Each step is its own request-log entry (`context.step`). For `anthropic/*` models the system prompt and the end of the stored conversation carry `cache_control` breakpoints (`with_cache_breakpoints`): every step and the next turn re-send them. The stored message has `parts` (text, prompt, and `run`/`tool` parts in order), `steps` (each step's content, tool calls and results, when tools were used), `notes` (new ones), `note_changes` (`{action: update|forget, id, text, previous}`), `cost` (summed), `request_id`/`request_ids`, and `automatic`/`error` when they apply. Prompts proposed go to history as before.
- **ComfyUI** (`comfy.py`, `comfy_graph.py`, `chat_tools.py`, `runs.py`, `workflows.py`, `catalog.py`). `comfy.client()` is the configured `Comfy` (or None): per run it picks the gateway, or ComfyUI directly only when the gateway doesn't answer the connection, and uses that URL for everything of the run (rules in `../comfyui-manager/docs/integracion.md`); jobs go with `extra_data.gateway = {project: "prompt-enhancer", priority: "high", tag: "conversar"}`. Images are saved in `output/prompt-enhancer/<conversation folder>/run-NN_seed-S_00001_.png` (`comfy.output_prefix`): the folder (`conversations.output_folder`, `<creation day>_<title slug>_<id[:8]>`) is named at the conversation's first run -- from its title, the title the bot is writing in that very reply (`ToolBox.title_hint`), or its first message -- and stored, so it never changes. `comfy_graph.Graph` is an API-format workflow and the edits the bot makes (ported from image-generation): prompt slots read from the main sampler, LoRA stack, seed, sampler settings, size, output prefix, add/remove/bypass/set; `generation_info()` reads the same things back. The tools: `run_workflow(workflow, changes, count)` (workflow = library name, `image:N`, or `run:N`; changes = positive/negative/seed/sampler/size/loras/input_images/set/add/remove; one job per image, each with its own seed; LoRA names resolved against the installed files by `catalog.resolve_file`), `inspect_workflow`, `list_comfy_models` (files plus what the catalog knows), `save_workflow` (new name, or `replace: true`), `cancel_run`. A run is recorded in the conversation's `runs` (`{n, workflow, changes, count, status, jobs: [{prompt_id, base_url, seed, status, images, error, models, loras}]}`) and `runs.tracker` (a thread started in `lifespan` when ComfyUI is configured, resuming pending runs after a restart) polls `/history` for its jobs, downloads their images into the conversation (with the job's workflow as their `.workflow.json`; nothing of a job is stored until all its images come down, and a failed download is tried again on the next polls, up to `MAX_DOWNLOAD_ATTEMPTS`, since ComfyUI stalls at times; a run whose downloads were given up can be fetched again with `POST …/runs/{n}/retry-downloads` -- the images are still in ComfyUI -- and they then go into its existing results message, with no new comment), and once the run is final appends a `{"role": "results", "run", "images"}` message and -- unless the user cancelled it, or other runs are still pending -- gives the bot an automatic turn to comment on them (`conversation_turn.on_run_finished`, `tool_choice: "none"`; skipped if the user wrote meanwhile). `catalog.py` keeps the installed checkpoints, diffusion models and LoRAs (LoRA base model and trigger words from `/view_metadata`), refreshed from ComfyUI once a day in the background (or from Ajustes) -- and its file list, names only, before every turn when older than `LISTING_MAX_AGE_SECONDS` (`ensure_fresh`/`refresh_files`, short timeout, old list kept if ComfyUI stalls; new LoRAs' metadata is then read in the background), so a model installed minutes ago is known. `match_installed` tells which installed file a resource named elsewhere is (same file name ignoring case, separators and folder; or most of its name's telling words, preferring its base model's folder; None when unclear), and `image_metadata.describe` uses it to tell the bot, per Civitai resource, "installed here as …" or "no installed file matches its name"; the owner's description of each, and per-file stats -- images made with it and how many the user liked or disliked -- computed from the runs and reactions. It also keeps each file's past use outside the app (`history`, `history_source`), imported once from comfy-gateway's job history by `gateway_history.py` as aggregates only: successful jobs, weights (median, min, max), the LoRAs it was most used with, the day last used. The aggregator reads nothing from a job but `status`, `finished_at` and `params.loras`/`params.models`; prompts, workflows, outputs and projects never reach the app (`python -m app.gateway_history aggregate jobs.json usage.json` where the history is, then `… import usage.json` -- or `-` for stdin -- where the data is). The raw history copies were deleted after the import (2026-11-03).
- **The family follows the base model.** Models live in a folder named after their family (`krea-2\…` is Krea 2), so `Graph.base_model_folder()` (the folder of its `ckpt_name`/`unet_name`, if exactly one) names a workflow's family and `families.family_for_folder` finds it by name ("Krea 2" ↔ `krea-2`). The library in the system prompt shows each workflow's family. When `run_workflow` is about to send a workflow (changes applied) whose base model is of another family than the conversation's -- `families.covers_folder` lets a variant like "Krea 2 - Ages" keep krea-2 models --, the conversation switches to that family and the run waits: the tool result hands the bot that family's rules (`family_rules`, elided from later turns, by then in the system prompt) to rewrite the prompt by and run again; the chat shows a `family` part. The reply is stored, and its prompts parsed and logged, by the family the turn ended in.
- **Switching family by name.** The system prompt names the current family (`## Model Family Rules: <name>`) and, with tools, lists the others (`## Model Families`); `use_family(name)` switches the conversation to one and hands over its rules (elided from later turns, by then in the system prompt) -- for when the user asks, or before writing for another family's model. The settings dropdown just shows the current family.
- **Mentioning images: `#N`.** Image N of the conversation is written `#N` by both sides (`chat.IMAGE_REF`, which skips `#ff0000`, `#1a`, `&#39;`, `##3`). The images the user's latest message mentions are attached to it again (`_referenced_images`, up to `MAX_REFERENCED_IMAGES`, with their metadata) when not attached anyway, so an old image can be talked about. In the chat, `#N` in either side's text renders as a link with the image's thumbnail that opens the viewer (`withImageRefs`), and typing `#` in the composer offers the conversation's images, newest first, to pick one (`renderPicker`).
- **Learning from runs.** In the reply that first sees a run's images the bot writes one `<review image="N" verdict="ok|flawed">what's wrong and its likely cause</review>` per image (`chat.parse_reply` → `reviews`), stored on the image (`conversations.set_review`) and so tied to its job's recipe. Every image that arrived since the bot last spoke is attached (up to `MAX_NEW_IMAGES`), not just the last `MAX_CONTEXT_IMAGES`, so it can review them all. A thumbs down needs its reason (400 without; the chat asks "¿Qué ha fallado?"). `catalog.stats()` counts per file: images, liked, disliked (latest reasons), flawed -- the bot's verdict, unless the user liked the image -- with the weights they failed at and the latest flaws, and for a LoRA its latest calibration (verdict per weight); the installed models list in the system prompt shows it compactly ("2 images, 1 flawed at 0.8, calibrated: fine up to 0.5, flawed from 1"), `list_comfy_models` in full. `calibrate_lora(lora, prompt, workflow?, weights?, keep_other_loras?)` makes one job per weight -- same prompt and seed, the LoRA set at that weight in the workflow's stack (or alone) -- at gateway priority `idle` (with a 12 h timeout, `run.timeout_seconds`), as a `kind: "calibration"` run whose results show each image's weight.
- **Isolation** (`comfy_policy.py`). The bot may only work with what the user gave it (library workflows, workflows embedded in images shared in the conversation) and what it made (its runs). Every workflow is checked before it is sent, and before `save_workflow` stores one: node types must come from the library, from workflows the user shared in this conversation, or `ALWAYS_ALLOWED` (core nodes that load nothing but model files), and never from `NEVER_ALLOWED` (nodes that read ComfyUI's folders, paths or URLs, like `LoadImageOutput`); any short string that looks like a file, path or URL must be one of this conversation's uploads (`input/prompt-enhancer/<conversation id>-<image id>.<ext>`). A saved workflow can't widen the allowed types (it is checked against them). `comfy.Comfy` itself only reads back what the app made: `view()` refuses anything but `output/prompt-enhancer/…` and the previews listed in its own jobs' `/history`, uploads go to `input/prompt-enhancer/`, model listings only for model folders, and nothing ever lists ComfyUI's queue or history (other projects' prompts and images live there).
- **Civitai** (`civitai.py`). A link to a Civitai image in a user message (`civitai.com/images/<id>`, also `civitai.green` and `civitai.red`, the same site; up to 4 images per message counting attachments) makes the app -- never the bot, which can't fetch anything -- read the image's record from Civitai's API (`/images?imageId=…&withMeta=true&nsfw=X`, with `CIVITAI_API_KEY` if set, which never goes to the image host), download the image and resolve the resources it was made with (`/model-versions/{id}` or `/by-hash/{hash}`: name, version, base model, trigger words, file, weight). It joins the message like an attached image, with that as its metadata (`source`, `resources`) and, if it was made with ComfyUI, its workflow (runnable as `image:N`). Any failure refuses the message with the reason (400), storing nothing.
- **Images** (`image_metadata.py`, Pillow). `conversations.save_image` stores the bytes as received, a `-small.jpg` copy when the image is large (what the LLM and the thumbnails get), and for a shared image its generation metadata (`image_metadata.read`: ComfyUI's PNG `prompt` chunk or EXIF `prompt:`, A1111-style `parameters` in PNG or EXIF UserComment) on the image record, with the embedded API workflow apart as `<id>.workflow.json`. Only picked or dropped files keep metadata; a pasted image has been re-encoded without it. **Reactions**: `PUT /api/conversations/{id}/images/{image_id}/reaction` (`{rating: "up"|"down"|null, comment}`) stores one on the image, unsent; the user's next message takes every unsent reaction (`conversations.append_message` moves them to the message's `reactions`), and a message may be just that.
- `POST /api/conversations` creates one (family, model, temperature, character ids); `GET`/`PATCH`/`DELETE /api/conversations/{id}` read it (plus `replying` / `commenting`: the bot is answering, or commenting on results, right now), change its settings or its title (the user's: the bot only titles an untitled conversation; neither moves `updated_at`), delete it with its images (a reply under way there then fails to store); `GET /api/conversations` lists summaries (title falling back to the first message; `last_reply_at`, the last assistant or results message, for the chat's "new reply" mark; `running`, a run pending; and `replying`/`commenting`), most recently updated first.
- `POST /api/conversations/{id}/messages` (multipart: `content` plus up to 4 `images`, all validated before any is stored; content may be empty when there are unsent reactions) appends the user message and returns a `StreamingResponse` of NDJSON events: `{"type": "delta", "text"}` while the reply arrives, `{"type": "tool", "part"}` for each tool call, then `{"type": "done", "message", "conversation"}` once it is stored, or `{"type": "error", "detail", "request_id"}` — by then the status is already 200, so failures travel as events. Only a finished reply is stored (or, if a later step fails after tools ran, what was done, with `error`). A failed reply leaves the user (or results) message last; `POST /api/conversations/{id}/reply` answers it again (409 if it already has a reply). `GET …/live` streams the reply being written there, from its start, with the same events (204 when there is none). `POST …/runs/{n}/cancel` cancels a pending run; `GET …/runs/{n}/workflow?job=` downloads the exact workflow sent; `GET …/images/{image_id}?small=true` serves the small copy.

**`routes/admin.py`** is a thin CRUD layer with no logic of its own — every endpoint is a one-line pass-through to `families`/`characters`/`memory`/`system_prompt` functions, translating `None`/`False` returns from those modules into 404s (`/api/admin/memory` is the bot's notes; Conversar's "Olvidar" and "Deshacer" go through it too), and `workflows.WorkflowError` into 400s. Besides those: `/api/admin/workflows` (the library; `POST …/extract` reads the workflow out of a ComfyUI image) and `/api/admin/catalog` (`GET`, `POST …/refresh` -- synchronous, reads ComfyUI --, `PUT …/description {file, text}`). System-prompt endpoints are parameterized by `mode`, validated against `VALID_SYSTEM_PROMPT_MODES` (the keys of `seed.DEFAULT_SYSTEM_PROMPTS`); `GET /api/admin/system-prompt/{mode}/default` returns the seed text so Ajustes can offer "Cargar el texto original" without overwriting anything. `routes/pages.py` only renders templates: the index gets the families, the Variaciones axes (labels from `prompts.VARIATION_AXES`, initial vary/fixed from `DEFAULT_VARYING_AXES`) and the default models; `/conversar` gets the families, the default model and whether ComfyUI is configured; historial and admin fetch their own data client-side.

**Frontend.** One Jinja2 template + one ES-module script per page, plus `static/common.js`, the one shared module: `request()` (fetch with timeout, JSON or FormData body, throws an `Error` carrying the server's `detail`), the `el()` DOM builder, `copyButton`, `setBusy`, the two-step `confirmButton` (no `window.confirm`), `toast`, the floating cost popup, and `renderTake(entry, handlers)` — the card that renders one generation (header, brief, "Abrir la conversación" for Conversar entries, a collapsible list of the Variaciones references with "Usar estas referencias", warnings, numbered frames with Copiar/Iterar/Añadir a referencias/Crear personaje) in both the workspace and Historial; a handler left out hides its action. `renderFrame` (one prompt as a frame, optionally numbered) is exported for Conversar's proposals, and `startConversationFrom(entry, prompt)` is what "Iterar" does everywhere: stash the prompt and settings in `sessionStorage["conversation-start"]` and go to `/conversar`, which opens a new conversation with "Partamos de este prompt: …" in the message box. It also owns the reference-prompt store (`loadReferences`/`storeReferences`/`mergeReferences` over `localStorage["reference-prompts"]`, capped at `MAX_REFERENCES`, matching the API's limit), shared because both pages add to it. The visual language (darkroom palette, the Archivo variable font served from `static/fonts/`, amber frame numbers) lives entirely in `style.css` tokens.
- `index.html`/`app.js` ("Crear"): a two-column workspace. The left composer has a mode tablist (Generar/Imagen/Historia/Variaciones) showing one `.mode-fields` block at a time over one shared form (characters, family, variants, and the collapsed model/temperature/examples section). `buildRequest()` validates per mode and returns the endpoint plus a JSON or FormData body. The right "sheet" lists the session's results newest-first (a pending card while waiting; capped at 30, persisted in `sessionStorage["workspace-takes"]`). Settings (mode, family, models, temperature, variants, examples, selected characters, story/variation counts, aesthetic and axes) persist in `localStorage["workspace-settings"]` (the pre-redesign `generar-settings` key is read once as a fallback). Characters are toggle chips plus a `<dialog>` to create/edit/delete them (through `/api/admin/characters`), which extract-character also opens prefilled. "Iterar" on any frame opens a conversation from it; "Añadir a referencias" appends it to the Variaciones reference list and switches there. That list is a column of textareas that always ends in one blank slot to paste into (until the limit); it is saved to `reference-prompts` on every edit and re-rendered on a `storage` event, so additions made from Historial in another tab show up live.
- `historial.html`/`historial.js`: client-side search (ideas, prompts, aesthetics, character names), mode/family/favorites filters, 25 entries per page, total cost of the filtered set. "Iterar" opens a conversation from the prompt (`startConversationFrom`). "Añadir a referencias" stays on the page (so several can be collected) and writes straight to the shared reference store; "Usar estas referencias" replaces the store with that entry's set and hands off `{family_id, llm_model, temperature}` in `sessionStorage["reuse-prompt"]`, which `app.js`'s `applyReuseHandoff()` applies before switching to Variaciones.
- `conversar.html`/`conversar.js` ("Conversar"): clicking an image opens the viewer (a `<dialog>` over the page, all the conversation's images browsable with the arrow keys; ctrl-click still opens a tab). Conversation list on the left (a drawer below 900px), the chat on the right with a settings panel (family, model, temperature, characters: kept in `state.draft` until the first message creates the conversation, `PATCH`ed after; the last ones used persist in `localStorage["conversation-settings"]`). Several conversations can be replying at once, and switching never waits: each reply under way is a `follow()` (one per conversation, in `state.live`) that reads its NDJSON stream with `fetch` + a body reader -- the POST that sent the message, or `GET …/live` to pick up one the chat didn't ask for (`attachIfReplying`: after a reload, in another tab, the bot's comment on results) -- keeps what arrived, and draws it only while its conversation is open; `liveParts()` (a JS mirror of `chat.parse_reply`, minus the bare-prompt fallback, which shows once the reply is stored) renders the partial reply, and the stored message replaces it on `done` (`settle`). The stream has an idle timeout (`STREAM_IDLE_MS`; the server's blank lines keep it alive); a cut connection doesn't end the reply, which is picked up again from the server. A request refused before anything was stored (`Rejected`) puts the text and images back in the composer (or in that conversation's draft, with a toast, if it isn't open); a failed reply leaves "Reintentar" with its reason (as does a conversation whose last message has no reply). The composer's text and attachments stay with their conversation when switching (`state.drafts`), and the send button is busy only in a conversation whose bot is at work. The list shows per conversation "Respondiendo…"/"Comentando…"/"Generando imágenes…", or "Respuesta nueva" (a dot) when something arrived since it was last open (`last_reply_at` against `localStorage["conversation-seen"]`), re-reading itself every `LIST_POLL_MS` while another conversation has something under way; each row renames (the title becomes a field: Intro or leaving saves, Escape drops) and deletes (two-step) on hover or focus, always on the open one. Proposals are numbered across the whole conversation, matching the ids the LLM sees, and fold to their number and first line with "Copiar" at hand (`proposal()`; the full frame body, shared with `renderFrame` as `common.frameBody`, when unfolded; which ones are unfolded is kept for the session). The bot's text goes through a small Markdown subset built as DOM nodes (no `innerHTML`). Each note the bot took shows as a chip with "Olvidar"; notes already gone from memory render as forgotten; a note it rewrote or forgot shows with "Deshacer" (restore the previous text, or recreate it). Images can be picked, pasted or dropped (4 per message); sending them to a model the model list marks as text-only is blocked. Every image shows its number (the one the bot sees); a shared image with metadata gets a collapsible panel with it. While streaming, `tool` events split the reply into segments, and each run the bot launched shows as a card (status, Cancelar, the workflow sent) that updates as the run goes; a results message is a contact sheet whose frames each have thumbs up/down and a comment (`PUT …/reaction`), and the composer says how many reactions will go with the next message (which may then be empty). While a run is pending or the bot is commenting on results, `schedulePoll()` re-reads the conversation every `POLL_MS` (only with the tab visible, not mid-typing a comment) and redraws what changed. The settings panel says whether the bot can run workflows with the chosen model (`supports_tools`).
- `peticiones.html`/`peticiones.js` ("Peticiones", linked from Ajustes, which the nav highlights): the request log, newest first, filterable by mode and errors, 50 per page; each row opens (fetching the full record once) to its facts, every message sent — images shown from the log — the reply as received, the error and raw error body, and copy buttons for the sent JSON and the reply. `?id=` shows just that request: it is where every "Ver la petición" link lands (`common.requestLink`, opening a new tab), from a Conversar reply or failure and from any take with `params.request_ids` (one link, or "Peticiones 1 2 3" for variants).
- `admin.html`/`admin.js` ("Ajustes"): one system-prompt editor with a tab per mode, keeping unsaved drafts per mode (dirty dot on the tab, `beforeunload` guard), where "Conversar" is the bot's personality; the bot's memory as a list of notes to add, edit inline or delete; families, characters and the ComfyUI workflows share the same `setupCrud()` list-plus-editor panel (a workflow is edited as API-format JSON, importable from a .json or from an image ComfyUI generated); "Modelos y LoRAs" lists the catalog, filterable, with a description field per file and "Actualizar desde ComfyUI".
